# Business creation and employee access

Agente de Larios. Requested goal: complete the business creation and employee login flows against PRD RF-01, RF-02 configuration, and RF-06 personal/device access. Existing sales/catalog/inventory modules retain their documented availability.

Google accounts resolve memberships on the server. An account without memberships sees Crear mi negocio / Unirme a un negocio; explicit /business/new opens creation. An owner creates business, first branch/register and operational profile plus confirmed PIN atomically. The editable profile contains branchName/registerName/address/city/state/contactPhone/paymentMethods; MXN remains fixed. Creation has a stable operation ID, loading/error and retry; Cuenta creada confirms account creation and links to Home. The owner can switch/add businesses from unlock and Home, edit profile, and recover/change PIN after fresh Google authentication.

An owner manages staff with roles manager/cashier/kitchen, individual PINs, active status and one-use expiring invitation codes. Google invitation acceptance creates a server-assigned membership and individual PIN; employee users cannot edit owner settings/team or see private owner configuration. A user may have a different role in each business. Deactivation revokes Google and device operator access.

For shared POS, an owner generates a one-use expiring pairing code. An unauthenticated tablet exchanges it for a restricted device secret, persisted locally as device identity and stored only as a hash on the server. Device status returns only basic business/register and active employee roster. PINs and operator tokens remain in memory. Switching/locking invalidates the previous operator before another login; refresh requires PIN, expiry returns roster, revocation removes access and the stored device credential. Every device request checks device and employee active state. No owner Google identity is used for a paired-device employee operation.

All sensitive decisions are transactional and server-enforced, with private RLS tables and service-role-only RPCs. Preserve current PIN attempt limits, Auth-session validity, tenant isolation, no-store requests, callback cancellation and cross-tab logout regressions. All financial/operational modules retain honest unavailable messages. Kitchen sees Comandas and Más; staff cannot access business/team settings.

Acceptance: owner creates persisted profile and re-enters after reload; can edit and manage staff; invitation code accepts once and rejects revoked/expired/reused codes, with safe retry; employee Google login uses assigned role; pairing code accepts once and rejects expired/revoked/reused codes; paired staff PIN unlock/switch/reload/lock/logout and owner revocation work; bad PIN lockout and foreign-tenant/admin access are denied; recovery demands fresh verified Auth session; desktop/mobile flows pass browser tests and real loopback backend tests without skipped integration suites.

Execution uses the current clean checkout with coordinated file ownership. Production publishing is a separate operation after verification; no new provider/expense or automatic external invitation message is introduced.
