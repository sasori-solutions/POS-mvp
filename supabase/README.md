## Trust boundary

The PWA uses only the project's public publishable/anon key. It calls `POST /functions/v1/account`. Personal commands send the Supabase Auth access token in `Authorization: Bearer …`; the function verifies it with `auth.getUser`, requires confirmed Google identity plus verified JWT OAuth AMR in production, and obtains the identity/session ID from that verified token. Browser-supplied identity fields are rejected. Restricted `device_*` commands use a random device credential validated by Postgres; pairing uses a one-use code. A public API key cannot establish either kind of business access.

All public `account_*` RPCs grant execution only to `service_role`. Personal RPCs check the current user/session against live `auth.sessions`; tenant actions also check matching active membership and employee records. An otherwise valid access JWT cannot continue accessing business data after its Auth session has been revoked. Owner settings/team commands additionally require an active owner operator session. Employees cannot call those commands, including when the interface is bypassed. Shared-device operator tokens belong to a separate table and cannot satisfy personal owner authorization.

All business, employee, credential, invitation, pairing, operation, session and audit tables live in `app_private`, with RLS enabled, no browser table/function grants, no permissive policies, and no exposure through the Data API. Security-definer entry points use an empty search path and fully qualified names. Do not add `app_private` to Supabase's exposed schemas. Future business commands must enforce the same tenant and operator-session checks; frontend visibility alone is insufficient.

## PINs and sessions

- PINs are exactly six ASCII digits, preserved as strings, including leading zeros. Postgres stores only salted bcrypt hashes at cost 12.
- Failed attempts are serialized with a credential row lock. Five failures lock that user/business for 15 minutes. The failure count survives rejected requests; expected PIN failures return values so transactions commit the counter. Creation retries cannot bypass this limit.
- An operator token has 256 bits of random entropy. Only its SHA-256 digest is stored server-side. The raw token belongs in frontend memory, never browser persistent storage, logs, or URLs.
- Personal tokens bind to the business, person, and Google Auth session, expire after eight hours, and are checked on every context request. Unlocking again replaces the active token for the same Auth session/business.
- `lock` is idempotent and revokes that token. `revoke_sessions` revokes this Auth session's operator tokens across businesses. Signout should call it before `auth.signOut({ scope: 'local' })`; the frontend always clears its own operator token, including when a network request fails. Auth session revocation is also checked server-side.
- Creation uses an owner-scoped UUID operation ID and serializes retries with a transaction advisory lock. Equal normalized business details/profile plus the same PIN return the existing business and a fresh operator session. Old creation payloads without a profile receive a principal branch/register and cash payment defaults. A changed payload returns `OPERATION_CONFLICT`; no unsalted digest of a six-digit PIN is stored.

## Progressive business setup and employees

The profile stores branch/register names, address, city/state, public contact phone and enabled payment methods (`cash`, `card_external`, `transfer`). Owner creation/settings validates and persists it; branch/register and at least one payment method are required when a profile is supplied. Fiscal, bank and provider credentials are excluded. `status` exposes business ID/name/type and non-secret `canRecoverPin`/`recoveryReady` flags; both recovery flags are false for employees. Personal employee context carries the server role and employee identity, with an empty profile projection. A paired register also gets only basic business details, its assigned register and PIN-ready active employee roster before PIN entry.

Roles are `owner`, `manager`, `cashier` and `kitchen`. The owner adds each employee through one form with name and assigned role. `create_employee` and `update_employee` accept only `pin: null`; both HTTP validation and SQL reject owner-written employee PINs. Optional Google access creates a pending employee/invitation atomically. PIN-only creation returns an explicit PIN setup authorization, without creating a credential. Existing PIN-only employees can receive a targeted Google invitation for the same employee ID. Staff updates change name/role/active state and revoke old operator sessions. Owners cannot demote/deactivate their own owner record through employee controls. Google membership activation and employee activation must both hold for personal staff access.

`create_pin_setup` authorizes initial setup or reset for one active, non-owner employee. Its random 256-bit code lasts 15 minutes and is stored only as a SHA-256 hash. A replacement authorization invalidates earlier codes and consumed retries while leaving the current PIN usable until consumption. Google-linked employees consume it only as their own live Google identity; PIN-only employees use a paired device for the same business. The recipient sees the assigned person/business, chooses and confirms the PIN, then `set_employee_pin` or `device_set_employee_pin` replaces the credential and closes that employee's old personal/register sessions atomically. The code neither links Google identities nor grants owner authority. Deletion, deactivation and Google linking invalidate prior setup authorizations. Exact lost-response retries require the original caller/operation, unexpired authorization and unchanged credential; they verify the current PIN counter instead of overwriting a later reset or clearing a subsequent lockout.

A personal invitation expires after 48 hours and is consumed in a row-locked transaction by one Google identity. `invitation_details` tells the recipient whether a PIN already exists. A PIN-less employee chooses a PIN once when joining. An employee with a shared-register PIN must enter that current PIN: acceptance preserves the exact salted hash and failure history while moving the credential to Google. Incorrect entry commits the shared failure count without consuming the invitation. Name/role and employee ID remain the owner's assigned values; the recipient does not repeat their name. Linking closes previous device operators, and personal/register entry then uses the same PIN and counter. Pending employees without a PIN stay off register rosters.

An exact acceptance retry verifies the current credential and its lockout before issuing a fresh operator; the original PIN cannot authenticate after a later change. A changed legacy request name conflicts; another person/operation cannot reuse a consumed invitation. Revoked and expired invitations fail. Name matching never merges employees. Previously issued invitation codes keep their explicit targets and hashes; retrying unconsumed invitation creation rotates its code, so the last returned code is current.

## Employee deletion, restoration and invitation outcomes

`delete_employee` and `restore_employee` require the active personal owner context, an explicit employee ID and a UUID operation ID. Owner records cannot be deleted/restored through these commands. Deletion is a reversible soft deletion: it sets `deleted_at`, deactivates the employee and any Google membership, closes personal/shared-register operator sessions and invalidates invitation codes, including old acceptance retries. Deleted employees cannot be edited, invited or resurrected by a creation retry. `team` returns them separately in `deletedEmployees`; the interface excludes them from the ordinary list and offers explicit restoration under Empleados eliminados.

Restoration returns the same employee ID, name, assigned role, Google identity, PIN credential and lockout counter. It reactivates the membership where applicable, but never revives old sessions or invitation codes; entry requires a new PIN unlock and a pending employee needs a fresh invitation. Each lifecycle operation records its authorized result. A repeated operation ID with the same action/target returns that result without reversing a later delete/restore; changing the action or target conflicts. A restore is an owner decision to return access, rather than an implicit side effect of editing a row.

Invitation summaries expose `status`, `expiresAt`, `acceptedAt`, `revokedAt` and `revokeReason` without credentials. Recorded cancellation/replacement/deletion/deactivation/linking reasons are distinct. Acceptance is a historical fact even if later deletion invalidates its old code; an expired invitation remains expired rather than becoming a fictitious cancellation. Cancelling an accepted invitation fails, and cancelling an already expired invitation does not invent a cancellation. Legacy database `created_at` and revocation reasons remain null when unknown. Only newly issued invitations receive a real database creation timestamp; legacy ordering does not expose an inferred creation date. Migration 0004 does not fabricate historical dates, alter expiry or replace existing codes. A separate real local 0003→0004 compatibility smoke verified those invariants.

The UI keeps invitations and PIN authorizations within the selected employee's focused detail. Owners see Autorizar creación de PIN/Restablecer PIN actions that generate authorization, with no employee PIN field. Invitation outcomes remain pending/accepted/cancelled/replaced/expired/unavailable with recorded dates. Unchanged saves are disabled. Focus/visibility/expiry refreshes preserve unsaved fields, while confirmed deletion or lost authorization clears the private detail and in-memory code.

## Shared registers and PIN recovery

An owner creates a one-use pairing code that expires after 10 minutes. Pairing assigns one business/register to a named device and returns a revocable 256-bit device credential with a 90-day lifetime. Only its SHA-256 hash is stored in Postgres. The client may persist this restricted credential to recognize the register; employee PINs and operator tokens stay in memory. Pairing retries use the same operation ID/device name, return the same device and rotate its credential; they invalidate previous device operators. A different operation cannot consume the code again. Pairing-code creation retries rotate an unused code on its existing row.

Every device request locks and validates the device row, including expiry/revocation. A device token alone can only read the basic business/roster or revoke itself; an individual employee PIN is required for context. Five wrong attempts lock for 15 minutes under concurrency. Google-linked employees and owners use the same credential/counter for personal and device PIN entry. A register PIN attempt replaces the previous operator, including on incorrect PIN; successful sessions expire after eight hours. Locking, switching staff, changing an employee, owner PIN recovery and device revocation invalidate old sessions. An owner PIN used at a shared register still grants only the device projection and cannot manage the business.

`create_recovery_code` requires a live personal owner operator, the current owner PIN and a UUID operation ID. Knowing the owner's Google session alone cannot enroll recovery. The code contains 256 random bits, is scoped to owner/business and is shown only in a successful response; the UI asks the owner to save it outside the shared browser. Only its SHA-256 hash is stored. New business setup generates it using the just-created operator and confirmed PIN. Existing businesses are deliberately unenrolled: the owner must unlock with the known PIN to create a code; there is no legacy Google-only fallback. Renewing the code invalidates its predecessor.

`reset_pin` requires that owner's independent recovery code, a UUID operation ID, fresh OAuth AMR in the verified JWT, and a live Google session whose original `auth.sessions.created_at` is at most five minutes old. Google alone is insufficient. Five wrong recovery attempts serialize and commit a separate 15-minute lockout, including concurrent requests. Success consumes the current code, changes the bcrypt PIN, clears the PIN counter, revokes all personal/register operators for that owner/business, issues a new personal operator and returns a replacement recovery code. Exact lost-response retries require the same consumed code/new PIN plus the still-current credential and code generation; they rotate an unseen replacement rather than storing raw codes. A retry after a later PIN/code change conflicts. Missing enrollment returns `RECOVERY_UNAVAILABLE`, wrong code `RECOVERY_INVALID`, and recovery cooldown `RECOVERY_LOCKED`.

`change_pin` is a separate action for the signed-in person. It requires that person's valid personal operator and current PIN, uses the ordinary PIN counter, changes only their own credential, closes their old personal/register operators and issues a replacement operator. It preserves an owner's recovery code. Exact retries require both salted prior/result PIN verification and an unchanged current credential, so they cannot overwrite a later PIN change or bypass cooldown.

A refreshed old JWT does not satisfy recent Google authentication. Password, magiclink, OTP and recovery sessions cannot qualify merely because the identity has linked Google. Production accepts only a Google/email identity set and rejects other linked OAuth providers. Recovery intent is bound to the selected business and the initiating owner identity; changing account cancels it. These actions and failed recovery attempts are audited without retaining raw PINs, codes or tokens.

Use `npm run db:reset` only for an explicitly disposable local database. Create a private, ignored `.env.functions` in the repository root containing:

```dotenv
ALLOWED_ORIGINS=http://127.0.0.1:5173,http://localhost:5173,http://127.0.0.1:5174
ALLOW_TEST_PASSWORD_AUTH=true
```

The CLI supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` automatically. The test password bypass requires both the flag and a local Supabase hostname (`localhost`, loopback, Docker `kong`, or `host.docker.internal`); it is rejected on hosted Supabase project URLs. Never configure this test flag for a hosted deployment.

For a separately authorized hosted deployment, apply all six checked-in migrations to a new database (or only pending migrations after verifying existing history), deploy `account`, and set `ALLOWED_ORIGINS` to the exact HTTPS PWA origin. The origin list must be nonempty; wildcards and insecure external origins are rejected. Set `[functions.account] verify_jwt = false`: the handler verifies Auth for personal commands and Postgres validates restricted device credentials for device commands, enabling consistent error shapes. Do not put a service key in any `VITE_*` variable.

Google OAuth additionally needs a Google Cloud Web OAuth client, its private secret configured in Supabase Auth, the Supabase callback URL registered at Google, and the actual PWA callback URL on Supabase's redirect allowlist. ## HTTP contract and observability

The shared TypeScript contract is `src/lib/contracts.ts`. Success responses have `{ data: … }`; failures have `{ error: { code, message, retryAfterSeconds? } }`. `status` returns business ID/name/type and owner recovery eligibility/readiness before PIN unlock. `create_business`, `unlock`, `accept_invitation`, `set_employee_pin`, `device_set_employee_pin`, `change_pin` and `device_unlock` return context plus an operator token/expiry. `reset_pin` additionally returns the replacement `recoveryCode`; `create_recovery_code` returns only that code. `create_pin_setup` returns `setupCode`, `setupId` and `expiresAt`; setup/invitation detail commands return the explicitly assigned employee/business projection. `context`/`device_context` return authorized context/expiry; `update_business` returns the business context directly. `team` excludes credentials; `create_employee` may include its generated Google invitation or PIN authorization. `delete_employee` returns `{ id, deleted: true }`, and `restore_employee` returns the employee summary. `device_status` exposes the basic business, PIN-ready active employees and assigned register. Expected errors expose no database details. Both PIN and recovery cooldowns return HTTP 429 with `Retry-After`.

Requests are JSON-only and capped at 8 KiB while streaming. Responses prohibit caching. CORS allows only configured origins. CORS is browser protection, while Auth, RPC grants, and SQL tenant checks provide authorization.

Private audit events record business/profile changes, employee/invitation/device operations, PIN success/failure/lockout/recovery, and operator revocation with server timestamps. They contain no PINs, tokens, email addresses, or request bodies. Unexpected function failures log only event, action, and stable database error code. Do not enable raw payload or RPC argument logging in external telemetry. Before pilots, schedule expired-session cleanup and define audit retention, alongside the broader backup/monitoring plan.
