# POS México account backend

Agente de Larios · 1 October 2026.

This slice supports Google sign-in, progressive business creation/settings, personal employee invitations, staff PIN management, a restricted shared-register login, device revocation, owner PIN recovery, and locking/sign-out. Sales and offline transactions remain subsequent slices. All account operations require a network connection.

## Trust boundary

The PWA uses only the project's public publishable/anon key. It calls `POST /functions/v1/account`. Personal commands send the Supabase Auth access token in `Authorization: Bearer …`; the function verifies it with `auth.getUser`, requires confirmed Google identity plus verified JWT OAuth AMR in production, and obtains the identity/session ID from that verified token. Browser-supplied identity fields are rejected. Restricted `device_*` commands use a random device credential validated by Postgres; pairing uses a one-use code. A public API key cannot establish either kind of business access.

All public `account_*` RPCs grant execution only to `service_role`. Personal RPCs check the current user/session against live `auth.sessions`; tenant actions also check matching active membership and employee records. An otherwise valid access JWT cannot continue accessing business data after its Auth session has been revoked. Owner settings/team commands additionally require an active owner operator session. Employees cannot call those commands, including when the interface is bypassed. Shared-device operator tokens belong to a separate table and cannot satisfy personal owner authorization.

All business, employee, credential, invitation, pairing, operation, session and audit tables live in `app_private`, with RLS enabled, no browser table/function grants, no permissive policies, and no exposure through the Data API. Security-definer entry points use an empty search path and fully qualified names. Do not add `app_private` to Supabase's exposed schemas. Future business commands must enforce the same tenant and operator-session checks; frontend visibility alone is insufficient.

## PINs and sessions

- PINs are exactly six ASCII digits, preserved as strings, including leading zeros. Postgres stores only salted bcrypt hashes at cost 12.
- Failed attempts are serialized with a credential row lock. Five failures lock that user/business for 15 minutes. The failure count survives rejected requests; expected PIN failures return values so transactions commit the counter. Creation retries cannot bypass this limit.
- An operator token has 256 bits of random entropy. Only its SHA-256 digest is stored server-side. The raw token belongs in frontend memory, never browser persistent storage, logs, or URLs.
- Personal tokens bind to the business, person, and Google Auth session, expire after eight hours, and are checked on every context request. Unlocking again replaces the active token for the same Auth session/business.
- `lock` is idempotent and revokes that token. `revoke_sessions` revokes this Auth session's operator tokens across businesses. Signout should call it before `auth.signOut({ scope: 'local' })`; the frontend always clears its own operator token, including when a network request fails. Auth session revocation is also checked server-side.
- Creation uses an owner-scoped UUID operation ID and serializes retries with a transaction advisory lock. Equal normalized business details/profile plus the same PIN return the existing business and a fresh operator session. Old creation payloads without a profile receive a principal branch/register and cash payment defaults. A changed payload returns `OPERATION_CONFLICT`; no unsalted digest of a six-digit PIN is stored.

## Progressive business setup and employees

The profile stores branch/register names, address, city/state, public contact phone and enabled payment methods (`cash`, `card_external`, `transfer`). Owner creation/settings validates and persists it; branch/register and at least one payment method are required when a profile is supplied. Fiscal, bank and provider credentials are excluded. `status` exposes only business ID/name/type. Personal employee context carries the server role and employee identity, with an empty profile projection. A paired register also gets only basic business details, its assigned register and active employee roster before PIN entry.

Roles are `owner`, `manager`, `cashier` and `kitchen`. The owner adds each employee through one form with name and assigned role. PIN-only access requires a confirmed PIN; optional Google access creates a pending employee and invitation atomically without a provisional PIN. Existing PIN-only employees receive a targeted Google invitation for the same employee ID. Staff updates change name/role/active state and optionally PIN; each update revokes that employee's old operator sessions. Owners cannot demote/deactivate their own owner record through employee controls. Google membership activation and employee activation must both hold for personal staff access. Deactivation removes the employee from register rosters and rejects later context/unlock calls.

A personal invitation expires after 48 hours and is consumed in a row-locked transaction by one Google identity. Acceptance links the invitation’s existing employee to the Google identity, creates membership and a salted personal PIN credential atomically, and retains the current owner-assigned name and role. The employee confirms their own PIN without entering their name again. Pending employees without a PIN stay off register rosters. Linking retires the shared credential and revokes old device operators while preserving its PIN lockout counter; personal and register entry then use the same credential. A retry with the same operation ID and data restores a fresh operator session without another membership. A changed legacy request name or PIN conflicts; a different person or operation cannot reuse a consumed invitation. Revoked and expired invitations fail. Creation is owner-scoped and idempotent; legacy name/role invitations cannot silently create another person when that name already exists, and require an explicit target instead. Name matching never merges employees. Migration `20261001000300_unified_employee_access.sql` binds previously issued invitations to explicit employees without changing their codes; only the SHA-256 hash of a random 256-bit secret is stored. Retrying invitation creation rotates its unconsumed code on the same invitation, so the last returned code is current.

## Shared registers and PIN recovery

An owner creates a one-use pairing code that expires after 10 minutes. Pairing assigns one business/register to a named device and returns a revocable 256-bit device credential with a 90-day lifetime. Only its SHA-256 hash is stored in Postgres. The client may persist this restricted credential to recognize the register; employee PINs and operator tokens stay in memory. Pairing retries use the same operation ID/device name, return the same device and rotate its credential; they invalidate previous device operators. A different operation cannot consume the code again. Pairing-code creation retries rotate an unused code on its existing row.

Every device request locks and validates the device row, including expiry/revocation. A device token alone can only read the basic business/roster or revoke itself; an individual employee PIN is required for context. Five wrong attempts lock for 15 minutes under concurrency. Google-linked employees and owners use the same credential/counter for personal and device PIN entry. A register PIN attempt replaces the previous operator, including on incorrect PIN; successful sessions expire after eight hours. Locking, switching staff, changing an employee, owner PIN recovery and device revocation invalidate old sessions. An owner PIN used at a shared register still grants only the device projection and cannot manage the business.

`reset_pin` is owner-only, verifies a fresh OAuth AMR timestamp in the already-verified JWT and a live Google session whose `auth.sessions.created_at` is at most five minutes old, stores the new bcrypt PIN, clears lockout, revokes all old personal/register sessions for that owner/business and issues a fresh personal operator session. A refreshed old JWT does not satisfy recent authentication. Password, magiclink, OTP and recovery sessions cannot qualify merely because the account has a linked Google identity. Supabase OAuth AMR does not identify a provider, so production accepts only a Google/email identity set and rejects other linked OAuth providers rather than treating their OAuth session as Google. The frontend performs a fresh Google sign-in for forgotten/changed PIN recovery. This action is audited without retaining either PIN.

## Local development and deployment

The repository root contains the CLI configuration. Start/reset the local stack with `npm run db:start` and `npm run db:reset`, then run `npm run api:serve`. Create a private, ignored `.env.functions` in the repository root containing:

```dotenv
ALLOWED_ORIGINS=http://127.0.0.1:5173,http://localhost:5173,http://127.0.0.1:5174
ALLOW_TEST_PASSWORD_AUTH=true
```

The CLI supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` automatically. The test password bypass requires both the flag and a local Supabase hostname (`localhost`, loopback, Docker `kong`, or `host.docker.internal`); it is rejected on hosted Supabase project URLs. Never configure this test flag for a hosted deployment.

For a separately authorized hosted deployment, apply all three checked-in migrations to a new database (or only pending migrations after verifying existing history), deploy `account`, and set `ALLOWED_ORIGINS` to the exact HTTPS PWA origin. The origin list must be nonempty; wildcards and insecure external origins are rejected. Set `[functions.account] verify_jwt = false`: the handler verifies Auth for personal commands and Postgres validates restricted device credentials for device commands, enabling consistent error shapes. Do not put a service key in any `VITE_*` variable.

Google OAuth additionally needs a Google Cloud Web OAuth client, its private secret configured in Supabase Auth, the Supabase callback URL registered at Google, and the actual PWA callback URL on Supabase's redirect allowlist. Google login cannot be verified until those credentials and redirect URLs exist.

Run focused validation with `deno test supabase/functions/account/validation.deno.ts supabase/functions/account/authentication.deno.ts` and typecheck with `deno check supabase/functions/account/index.ts`. The repository integration tests exercise the real local Auth, Edge Function, and Postgres; they use synthetic local users only. Deleting an Auth user cascades credentials, memberships, sessions, and operation records; business records remain deliberately independent of Auth account deletion. Reset the disposable local database for a clean test run. `node tests/integration/real-onboarding-smoke.mjs` additionally launches a dedicated Vite server on loopback port 5175 and exercises the actual browser/client/function/database contract without API mocks (allow that origin in the local function). It verifies business/profile creation, the single employee form, atomic Google pending access, same-ID linking without duplicate staff, old PIN/operator invalidation, device pairing/PIN/revocation and personal returning PIN, then removes its synthetic fixtures. `node tests/integration/production-google-guard.mjs` must instead run with the local function password bypass disabled; it adds a synthetic linked-Google identity and proves actual password/magiclink JWTs cannot read an account or reset its PIN. Never use either script against cloud.

## HTTP contract and observability

The shared TypeScript contract is `src/lib/contracts.ts`. Success responses have `{ data: … }`; failures have `{ error: { code, message, retryAfterSeconds? } }`. `status` returns only business ID, name, and type before PIN unlock. `create_business`, `unlock`, `accept_invitation`, `reset_pin` and `device_unlock` return business context plus an operator token/expiry. `context`/`device_context` return authorized context/expiry. `update_business` returns the business context directly. `team` returns employees, invitation summaries and device summaries without credentials; employee mutations return an employee summary directly. `device_status` returns the basic business, active employees and assigned register. Lock/revoke actions return acknowledgement flags. Expected codes never contain database details. PIN lockouts return HTTP 429 with `Retry-After`.

Requests are JSON-only and capped at 8 KiB while streaming. Responses prohibit caching. CORS allows only configured origins. CORS is browser protection, while Auth, RPC grants, and SQL tenant checks provide authorization.

Private audit events record business/profile changes, employee/invitation/device operations, PIN success/failure/lockout/recovery, and operator revocation with server timestamps. They contain no PINs, tokens, email addresses, or request bodies. Unexpected function failures log only event, action, and stable database error code. Do not enable raw payload or RPC argument logging in external telemetry. Before pilots, schedule expired-session cleanup and define audit retention, alongside the broader backup/monitoring plan.
