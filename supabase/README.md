## Trust boundary

The PWA uses only the project's public publishable/anon key. It calls `POST /functions/v1/account`. Personal commands send the Supabase Auth access token in `Authorization: Bearer …`; the function verifies it with `auth.getUser`, requires confirmed Google identity plus verified JWT OAuth AMR in production, and obtains the identity/session ID from that verified token. Browser-supplied identity fields are rejected. Restricted `device_*` commands use a random device credential validated by Postgres; pairing uses a one-use code. A public API key cannot establish either kind of business access.

All public `account_*` RPCs grant execution only to `service_role`. Personal RPCs check the current user/session against live `auth.sessions`; tenant actions also check matching active membership and employee records. An otherwise valid access JWT cannot continue accessing business data after its Auth session has been revoked. Owner settings/team commands additionally require an active owner operator session. Employees cannot call those commands, including when the interface is bypassed. Shared-device operator tokens belong to a separate table and cannot satisfy personal owner authorization.

All business, employee, credential, invitation, pairing, operation, session and audit tables live in `app_private`, with RLS enabled, no browser table/function grants, no permissive policies, and no exposure through the Data API. Security-definer entry points use an empty search path and fully qualified names. Do not add `app_private` to Supabase's exposed schemas. Future business commands must enforce the same tenant and operator-session checks; frontend visibility alone is insufficient.

## PINs and sessions

- PINs are exactly six ASCII digits, preserved as strings, including leading zeros. Postgres stores only salted bcrypt hashes at cost 12.
- Failed attempts are serialized with a credential row lock. Five failures lock that user/business for 15 minutes. The failure count survives rejected requests; expected PIN failures return values so transactions commit the counter. Creation retries cannot bypass this limit.
- An operator token has 256 bits of random entropy. Only its SHA-256 digest is stored server-side. The raw token belongs in frontend memory, never browser persistent storage, logs, or URLs.
- Personal tokens bind to the business, person, and Google Auth session, expire after eight hours, and are checked on every context request. Unlocking again replaces the active token for the same Auth session/business.
- `lock` is idempotent and revokes that token. `revoke_sessions` revokes this Auth session's operator tokens across businesses. Signout should call it before `auth.signOut({ scope: 'local' })`; the frontend always clears its own operator token, including when a network request fails. Auth session revocation is also checked server-side.
- Creation uses an owner-scoped UUID operation ID and serializes retries with a transaction advisory lock. Equal normalized business details/profile plus the same PIN return the existing business and a fresh operator session. Old creation payloads without a profile receive a principal branch/register and cash payment defaults. A changed payload returns `OPERATION_CONFLICT`; no unsalted digest of a six-digit PIN is stored.

## Progressive business setup and employees

The profile stores branch/register names, address, city/state, public contact phone and enabled payment methods (`cash`, `card_external`, `transfer`). Owner creation/settings validates and persists it; branch/register and at least one payment method are required when a profile is supplied. Fiscal, bank and provider credentials are excluded. `status` exposes business ID/name/type and non-secret `canRecoverPin`/`recoveryReady` flags for active personal memberships. A recovery request separately verifies the confirmed account email and existing PIN. Personal employee context carries the server role and employee identity, with an empty profile projection. A paired register also gets only basic business details, its assigned register and PIN-ready active employee roster before PIN entry.

Roles are `owner`, `manager`, `cashier` and `kitchen`. The owner adds each employee through one form with name and assigned role. `create_employee` and `update_employee` accept only `pin: null`; both HTTP validation and SQL reject owner-written employee PINs. The current UI creates a pending employee/Google invitation atomically. The API retains legacy PIN-only creation with an explicit PIN setup authorization and no credential. Existing PIN-only employees can receive a targeted Google invitation for the same employee ID. Staff updates change name/role/active state and revoke old operator sessions. Owners cannot demote/deactivate their own owner record through employee controls. Google membership activation and employee activation must both hold for personal staff access.

`create_pin_setup` authorizes initial setup or reset for one active, non-owner employee. Its random 256-bit code lasts 15 minutes and is stored only as a SHA-256 hash. A replacement authorization invalidates earlier codes and consumed retries while leaving the current PIN usable until consumption. Google-linked employees consume it only as their own live Google identity; PIN-only employees use a paired device for the same business. The recipient sees the assigned person/business, chooses and confirms the PIN, then `set_employee_pin` or `device_set_employee_pin` replaces the credential and closes that employee's old personal/register sessions atomically. The code neither links Google identities nor grants owner authority. Deletion, deactivation and Google linking invalidate prior setup authorizations. Exact lost-response retries require the original caller/operation, unexpired authorization and unchanged credential; they verify the current PIN counter instead of overwriting a later reset or clearing a subsequent lockout.

A personal invitation expires after 48 hours and is consumed in a row-locked transaction by one Google identity. `invitation_details` tells the recipient whether a PIN already exists. A PIN-less employee chooses a PIN once when joining. An employee with a shared-register PIN must enter that current PIN: acceptance preserves the exact salted hash and failure history while moving the credential to Google. Incorrect entry commits the shared failure count without consuming the invitation. Name/role and employee ID remain the owner's assigned values; the recipient does not repeat their name. Linking preserves the PIN and counter but closes previous register operators; Google-linked employees then use their personal linked browser, not the shared-register path. Pending employees without a PIN stay off register rosters.

An exact acceptance retry verifies the current credential and its lockout before issuing a fresh operator; the original PIN cannot authenticate after a later change. A changed legacy request name conflicts; another person/operation cannot reuse a consumed invitation. Revoked and expired invitations fail. Name matching never merges employees. Previously issued invitation codes keep their explicit targets and hashes; retrying unconsumed invitation creation rotates its code, so the last returned code is current.

## Permanent employee deletion and invitation outcomes

`delete_employee` requires an active personal owner context, an explicit employee ID and a UUID operation ID. Owner records cannot be deleted through this command. Deletion removes the employee row and that business's Google membership, PIN credentials/counters, personal and register operator sessions, personal device binding, notifications, invitations, PIN setup codes and recovery authorizations. Audit events remain with the removed employee's user/session references cleared. The global Auth account and access to other businesses are preserved. `restore_employee` is rejected as `VALIDATION_ERROR`; `team` has no `deletedEmployees` archive and the interface has no restoration action.

Returning employees need a new owner invitation, which creates a new employee ID. The recipient chooses a new PIN and enrolls the browser used for acceptance, even when using the same Google account or browser as before. The old PIN, operator tokens, links and device approvals cannot authorize the new employee. Active PIN-only employees can still link Google to their existing identity by proving their current PIN; deletion does not use that path.

Posted sales keep their immutable receipt snapshots, while their employee reference and saved POS operation actor reference become null. Operation IDs remain reserved, and an employee created by reinvitation cannot replay the removed employee's sale operation. Removing an employee does not erase the business's financial history.

Opaque operation tombstones prevent old employee/invitation creation retries from recreating removed access. A repeated deletion operation for the same business and employee returns `{ id, deleted: true }` without changing a later employee; a different target/business conflicts. Owner creation, invitation and deletion take a shared business mutation lock, and employee/credential row locks serialize credential operations with removal. Short-lived global signed-request nonce records remain to reject request replay; they contain no PIN or device private key. Migration 0011 also purges previously soft-deleted employees and prohibits new soft-deleted rows.

Invitation summaries for existing employees expose `status`, `expiresAt`, `acceptedAt`, `revokedAt` and `revokeReason` without credentials. Cancellation/replacement/deactivation/linking reasons remain distinct; permanent employee deletion removes that employee's invitation rows entirely. An expired invitation remains expired rather than becoming a fictitious cancellation. Cancelling an accepted invitation fails, and cancelling an already expired invitation does not invent a cancellation. Legacy database `created_at` and revocation reasons remain null when unknown. Only newly issued invitations receive a real database creation timestamp; legacy ordering does not expose an inferred creation date. Historically, migration 0004 did not fabricate dates, alter expiry or replace existing codes; the separate 0003→0004 compatibility smoke continues to verify that historical migration's behavior.

The UI keeps invitations and PIN authorizations within the selected employee's focused detail. Owners see Crear código para PIN/Crear código para restablecer PIN actions that generate authorization, with no employee PIN field. Invitation outcomes remain pending/accepted/cancelled/replaced/expired/unavailable with recorded dates. Unchanged saves are disabled. Focus/visibility/expiry refreshes preserve unsaved fields, while confirmed deletion or lost authorization clears the private detail and in-memory code.

## Shared registers and PIN recovery

An owner creates a one-use pairing code that expires after 10 minutes. Pairing assigns one business/register to a named device and returns a revocable 256-bit device credential with a 90-day lifetime. Only its SHA-256 hash is stored in Postgres. The client may persist this restricted credential to recognize the register; employee PINs and operator tokens stay in memory. Pairing retries use the same operation ID/device name, return the same device and rotate its credential; they invalidate previous device operators. A different operation cannot consume the code again. Pairing-code creation retries rotate an unused code on its existing row.

Every device request locks and validates the device row, including expiry/revocation. A device token alone can only read the basic business/roster or revoke itself; an individual employee PIN is required for context. Five wrong attempts lock for 15 minutes under concurrency. Google-linked non-owner employees cannot unlock shared registers; their personal entry enforces browser binding. Owners retain the restricted register projection when entering by PIN. A register PIN attempt replaces the previous operator, including on incorrect PIN; successful sessions expire after eight hours. Locking, switching staff, changing an employee, owner PIN recovery and device revocation invalidate old sessions. An owner PIN used at a shared register still grants only the device projection and cannot manage the business.

`request_pin_email` requires a live personal identity and active membership; `device_request_pin_email` requires a valid paired-device credential and a linked person in that business. The server selects the confirmed account address. It limits requests to five per hour with a 60-second minimum interval, replaces earlier links and reports sent only after the mail provider accepts delivery. The random 256-bit link is stored as a hash and expires after 15 minutes.

`pin_email_details` inspects the link without consuming it. `confirm_pin_email` verifies delivery, expiry, active membership, unchanged confirmed email and prior PIN hash, then changes the PIN, consumes the link and closes that person's operators. It requires neither Google reauthentication nor the old recovery code, and issues no Auth/operator session. An exact operation retry reports completion only while its result PIN hash remains current. Email recovery requires a linked account with a confirmed email; owner-authorized employee PIN setup/reset remains a separate flow.

`change_pin` requires the signed-in person's valid personal operator and current PIN. It uses the ordinary PIN counter, closes prior operators and returns a replacement operator. Exact retries cannot overwrite a later PIN or bypass cooldown. Recovery does not change the personal browser binding or authorize a device replacement.

The HTTP validator and public SQL dispatcher reject the retired `create_recovery_code` and `reset_pin` actions. Their 0006 implementation and tests remain historical migration evidence. Production personal authentication accepts only the Google/email identity set and checks OAuth AMR; password, magiclink and OTP sessions cannot qualify merely because Google is linked. Email confirmation authorizes only the scoped PIN reset. PINs, raw links and tokens must not be logged or persisted by the browser. See [email recovery](../docs/pin-email-recovery.md) for the complete contract.

```dotenv
ALLOWED_ORIGINS=http://127.0.0.1:5173,http://localhost:5173,http://127.0.0.1:5174
ALLOW_TEST_PASSWORD_AUTH=true
```

The CLI supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` automatically. The test password bypass requires both the flag and a local Supabase hostname (`localhost`, loopback, Docker `kong`, or `host.docker.internal`); it is rejected on hosted Supabase project URLs. Never configure this test flag for a hosted deployment.

For an authorized hosted backend deployment, verify the linked project and migration history first. Apply the complete migration chain through 0011 only to a new database; for the existing project, apply only verified pending migrations after reviewing the permanent-unlink purge preflight. Deploy and verify the compatible `account` function **before merging any dependent frontend PR**. Every checked push to `main` automatically deploys the frontend; CI does not deploy Supabase. Confirm compatibility with the currently hosted frontend and coordinate any required cutover before merging. Follow [DEPLOYMENT.md](../DEPLOYMENT.md), record backend evidence in the PR, and set `ALLOWED_ORIGINS` to the exact HTTPS PWA origin. The origin list must be nonempty; wildcards and insecure external origins are rejected. Set `[functions.account] verify_jwt = false`: the handler verifies Auth for personal commands and Postgres validates restricted device credentials for device commands, enabling consistent error shapes. Do not put a service key in any `VITE_*` variable.

## HTTP contract and observability

The shared TypeScript contract is `src/lib/contracts.ts`. Success responses have `{ data: … }`; failures have `{ error: { code, message, retryAfterSeconds? } }`. `status` returns business ID/name/type and recovery flags for active personal memberships before PIN unlock. `create_business`, `unlock`, `accept_invitation`, `set_employee_pin`, `device_set_employee_pin`, `change_pin` and `device_unlock` return context plus an operator token/expiry. `request_pin_email`/`device_request_pin_email` return `{ sent: true, retryAfterSeconds }`; `pin_email_details` returns business name/expiry; `confirm_pin_email` returns `{ updated: true }` without an operator session. Legacy `reset_pin`/`create_recovery_code` actions are rejected. `create_pin_setup` returns `setupCode`, `setupId` and `expiresAt`; setup/invitation detail commands return the explicitly assigned employee/business projection. `context`/`device_context` return authorized context/expiry; `update_business` returns the business context directly. `team` excludes credentials; `create_employee` may include its generated Google invitation or PIN authorization. `delete_employee` returns `{ id, deleted: true }`; `restore_employee` is no longer accepted. A fresh invitation returns a new employee ID with `pinReady: false` when no PIN exists; there is no `returningEmployee` restoration response. `device_status` exposes the basic business, PIN-ready active employees and assigned register. Expected errors expose no database details. Both PIN and recovery cooldowns return HTTP 429 with `Retry-After`.

Requests are JSON-only and capped at 8 KiB while streaming. Responses prohibit caching. CORS allows only configured origins. CORS is browser protection, while Auth, RPC grants, and SQL tenant checks provide authorization.

Private audit events record business/profile changes, employee/invitation/device operations, PIN success/failure/lockout/recovery, and operator revocation with server timestamps. They contain no PINs, tokens, email addresses, or request bodies. Unexpected function failures log only event, action, and stable database error code. Do not enable raw payload or RPC argument logging in external telemetry. Before pilots, schedule expired-session cleanup and define audit retention, alongside the broader backup/monitoring plan.
